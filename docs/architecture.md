# 架构

这份文档解释墨井为什么这样切分，以及每一层的边界在哪里。想改代码之前先读这一篇。

## 一句话结构

```text
src/
  domain/    纯函数与磁盘读写，不认识 DSH，可以在 node 里直接测
  panel/     面板投影、抽屉树与路由（model/tree/dirs/entry/edit/roles/catalog 纯函数，serve.ts 一个 prefix handler）
  tools/     九个工具，只做参数翻译与结果格式化
  gate.ts    预执行门禁，唯一能拒绝调用的地方
  index.ts   挂载：注册工具 + 挂 tools/pre-execute + 挂面板路由
client.js    浏览器半边：把面板注册成右侧栏的一个 tab 类型，并调宿主的目录选择框
```

`domain/` 不认识 Cordis，也不认识工具注册表。这是刻意的：约束逻辑必须是可单测的纯函数，否则「代码强制」会退化成「代码看起来在强制」。

## 为什么记忆放在项目目录里

主流做法是把记忆挂在会话上：把前情摘要注入上下文，靠 session 存。问题有三个：

1. **会话是复盘用的，不是检索用的。** append-only 事件流适合人看，不适合按「沈砚的左眼」去查。
2. **换会话就丢。** 用户新开一个窗口，模型就重新开始编。
3. **摘要会蒸发细节。** 「他改了航向」这种摘要，丢掉的正是后面会冲突的那个事实。

所以墨井把状态落在 `<root>/` 下，纯 JSON + Markdown：

```text
<root>/
  project.json          阶段、前提、目标字数、本书的角色路由覆盖
  canon/characters.json 角色卡（含 voice）
  canon/world.json      世界观条目
  outline/volumes.json  分卷
  outline/chapters.json 章纲（含 beats）
  ledger/facts.json     事实账本
  chapters/index.json   章节索引（字数、摘要）
  chapters/001.md       正文，一章一文件
  drafts/001/01.json    草稿轮次（propose 落在这里，commit 才进 chapters）
```

写入统一走「临时文件 + rename」，进程被杀不会留下半截设定。正文用 Markdown，用户随时可以用编辑器直接改，改完再让工具读。

### 根目录属于会话，不属于进程

v0.2 在挂载时就把 `root` resolve 成绝对路径，存进一个长生命周期的 `ProjectStore`。单个工作区时没问题，多个工作区时第二个窗口会静默接管第一本书的 canon——这是最难查的一类串稿。

现在这条规则只有一个实现，在 `src/domain/scope.ts`：

```text
resolveSessionRoot(exec, config, baseStore):
  perWorkspace 关 → baseStore                    （v0.2 行为）
  root 是绝对路径 → baseStore                    （一本书，钉死）
  否则读 exec.agent.session.header.cwd
    有这个 cwd → new ProjectStore(resolve(cwd, root))
    没有       → baseStore                       （宁可共用，不可猜错书）
```

三个关键选择：

1. **`cwd` 来自会话头**，不是 `process.cwd()`。`SessionHeader.cwd` 是 DSH 在创建会话时记录的绝对工作目录，正是「这个窗口在看哪个项目」的权威答案。
2. **工具和门禁共用同一个解析**。`gateToolCall` 拿到的 `exec` 和 `execute` 拿到的是同一个，两边必须算出同一本书，否则会出现「在这本书上批准、往另一本书里写」。
3. **读不到 `cwd` 就退回共享 store**。猜错书的代价（写坏别人的书）远大于共用一本（用户看到「这本书里没这个项目」）。

`ToolDeps` 因此不再持有 `store`，而是持有 `storeFor(exec)`。这个接口变化是刻意的：让「哪本书」变成一个必须用调用上下文回答的问题，而不是一个可以在挂载时拍死的常量。

## 阶段机

阶段只能前进，且每个阶段的目标由数据判定，不由模型声明。

| 目标阶段 | 必须满足 |
|---|---|
| `canon` | 前提字数 ≥ `premiseMinChars` |
| `outline` | ≥1 主角、≥2 角色、≥1 世界观、每个角色有 `voice` |
| `drafting` | ≥1 已批准分卷、≥1 章纲、每章 ≥2 节拍、章纲人物都在角色卡里 |
| `review` | 至少写完 1 章、所有章纲都已落笔 |

`voice` 被列进硬条件，是因为「千人一腔」在长篇里比情节漏洞更致命：它不是某一章的错误，而是全程的错误。

## 事实账本

一条事实是四元组加一个来源：

```json
{ "id": "f-0001", "subject": "沈砚", "predicate": "左眼颜色",
  "value": "黑", "chapter": 3, "quote": "他的左眼黑得像井",
  "supersedes": null }
```

写入规则：

| 情况 | 结果 |
|---|---|
| 同主体同属性，值相同 | 视为重复，不重复写入 |
| 同主体同属性，同章不同值 | **拒绝**（同一章内自相矛盾） |
| 同主体同属性，异章不同值，无 `supersedes` | **拒绝**（跨章改动要有交代） |
| 带 `supersedes` 指向旧条目 | 通过，旧条目失效 |

第三条是最有争议的一条：人物确实会变（断臂、失忆）。要求 `supersedes` 不是禁止变化，而是**强迫变化留下痕迹**。这样「他什么时候瞎的」永远查得到。

比较用 `foldKey()`：全角转半角、去空白、小写。所以「左眼 颜色」和「左眼颜色」是同一条。

## 章纲合同

章纲是承诺：这些节拍、这些人、这个视角。写完之后逐项核对。

| 检查 | 严格度 | 理由 |
|---|---|---|
| 必出场角色是否出现 | **error，拒绝保存** | 名字是精确子串，没有歧义 |
| 章纲视角人物是否出现 | warn | 第一人称时人物名可能不出现 |
| 字数区间 | warn | 平台要求不同 |
| 节拍覆盖 | warn | 只能按二元字组估算，不能当判决 |
| 章末钩子 | info | 字面出现与否不等于悬念成立 |

节拍覆盖用二元字组：把节拍和正文都切成相邻两字，算重合比例，低于 `beatCoverageMin` 就提示，并把缺的词列出来。这是**宁可漏报**的设计——误杀一章 3000 字的稿子，代价远大于漏掉一次提醒。

## 确定性边界

分清哪些是判决、哪些是提醒，是这个项目最重要的自觉：

- **判决（会拒绝）**：阶段条件、章纲人物缺失、账本冲突、参数非法。
- **提醒（只报告）**：节拍覆盖、复读、句式、节奏、套路词、对话占比、章末钩子。

提醒类的阈值全部可配。不同题材对「套路」的定义不同，写死在代码里就是把作者的品味强加给用户。

## 角色路由的三态

每个角色的模型路由是四个字段（`provider` / `model` / `maxTokens` / `reasoningEffort`），每层都可以对某个字段说话，也可以什么都不说。三种状态，缺一不可：

| 状态 | 写法 | 含义 |
|---|---|---|
| 不提 | 字段缺失 | 交给下一层 |
| 钉住 | 一个值 | 本书就用这个 |
| 显式不设 | `null`（工具层用空串 / `0` 表达） | 压住下一层，本书这一项就是空 |

只有前两态是不够的：全局配了 `reasoningEffort: high`，某本书想对写手关掉它，如果没有第三态，唯一办法是把整个角色覆盖删掉，顺手把 `model` 也丢了。合并逻辑在 `src/domain/fields.ts`，逐字段独立求值，所以清一项不会连累邻居。

`reasoningEffort` 的类型是 `ReasoningEffortId`（DSH 的 branded 字符串），取值由供应商适配器决定，插件只透传——把 `low/high` 写死在插件里，等于替所有人选了同一家的档位。

## 与 DSH 的接缝

宿主侧用了四个扩展点：

1. `ctx.tools.register(defineTool({...}))` —— 注册工具，schema 自动进入系统提示词组装。
2. `ctx.on('tools/pre-execute', (exec, next) => ...)` —— 预执行瀑布，返回 `{kind:'deny', reason}` 即拦截，`next()` 放行。
3. `ctx.inject(['webServer'], …)` + `webServer.register({kind:'prefix', path:'/api/inkwell'})` —— 面板的只读数据接口。
4. 客户端半边：`client.js` 里的 `ctx.sidebarRightTabs.register(…)` —— 把面板注册成右侧栏的一个 tab 类型。

派发角色时多用一层 `ctx.subagents.start('spawn', …)`，但它不是「拒绝」通道：那里只负责起子智能体并收集文本。

门禁放在 `pre-execute` 而不是 `execute` 里，是为了让被拒的调用**不产生任何副作用**，同时把拒绝原因作为工具结果回给模型——模型看到的是「还缺什么」，而不是一个异常堆栈。

## 面板为什么不走 Remote

DSH 有两套往界面送数据的办法：Remote 命名空间（宿主面 + 客户端面靠 bundle manifest 配对）和 HTTP 路由。面板选了后者，理由很实际：**它只有一处写，而且那一处已经是工具允许的**。Remote 那一套的价值在于双向类型契约，而这张快照是只读投影，写只有「建书」一个动作——为一个动作拉整层机械不值。

于是形状变成：

```text
src/domain/save.ts   纯函数 + 一次写盘：正文落盘的唯一入口，工具与面板共用
src/panel/model.ts   纯函数：Snapshot → PanelSnapshot（阶段、进度、事实、线索）
src/panel/tree.ts    纯函数：Snapshot → 四个抽屉（世界/人物/剧情/正文），带计数与状态
src/panel/entry.ts   纯函数：一行 → 一页（fields + lists + breadcrumb + edit），角色/设定/章节三种
src/panel/edit.ts    纯函数：三个 readXxxPatch，写门的字段校验与上限
src/panel/library.ts 书架：记住了哪些目录是书，读回时逐个验明还在不在
src/panel/serve.ts   路由：读投影、书库、详情与团队，序列化 JSON，处理 /init、/dirs 与 /entry
src/panel/dirs.ts    纯函数 + 一层 readdir：列目录，回报该目录里有没有书
client.js            浏览器半边：先书库再抽屉树，每 15 秒 GET 一次，渲染成抽屉树、详情页与设置页
```

`model.ts`／`tree.ts`／`entry.ts`／`dirs.ts`／`edit.ts`／`library.ts` 都不认识 Cordis，也不认识 HTTP——和 `domain/` 的同一条理由：面板上显示的东西必须能在 node 里直接断言。

详情页的载荷是**通用形状**（`fields` 加 `lists`，外加可编辑的 `edit.inputs` 与 `edit.body`），不是三套写死的模板：加第四种页面只改 `entry.ts`，`client.js` 那半边一行都不用动。这是把一个组件写两次和写一次的分界——浏览器不该知道「角色」有什么字段，也不该知道哪些字段能改。

正文之所以能从两个地方写进来而不打架，是因为**只有一处落盘**：`saveChapterBody(store, config, input)` 在 `src/domain/save.ts` 里跑合同与体检，`novel_chapter action="write"` 和 `POST /entry` 都只调用它一次。规则复制一份到面板里，两边迟早会分叉成「工具不让写、面板却写得进」。

服务是**可选**的：`webServer` 经 `ctx.inject` 等，headless profile 里没有它，插件就只装工具不装面板。反过来，如果把它写进 `inject` 导出，headless 下的插件会整个不激活——一个面板不该有这种权力。

### 书库：列表是提示，磁盘是事实

一本书就是一个装着 `project.json` 的目录，没有任何索引能把它找出来。面板因此维护一份书架（`$DSH_HOME/inkwell/books.json`，没有 `DSH_HOME` 就是 `~/.dsh`），只记路径与时间，最近 40 条。`GET /books` 把三处并起来：请求里 `?root=` 指定的、会话解析出的、书架上记着的——**每一处都要过一遍磁盘**（`describeBook` 先 `exists()` 再读 `project.json`）。

这条「都要验明」的规矩不是洁癖：书架记的是路径，路径会过期。目录被删、被搬走、被改名之后，一份不验的书架会把一本书永远列在第一位，而点进去只能得到「这里没有书」。所以书架只负责**让人少点几次目录**，不负责断言存在；`test/panel.test.ts` 里有一条专门删掉目录再问 `/books`。

排序也是个决定：当前会话那本永远第一，其余按 `project.json` 的 `updatedAt` 倒序。前者是「继续写」，后者是「最近动过的」——两个问题不一样，混在一起排会让「继续写」沉到列表中间去。

`rememberBook` 只在书不在第一位时才写盘。快照路由每 15 秒轮询一次，每次都 `readFile` 一份几十行了列表无所谓，每次都 `writeFile` 就是拿读者的磁盘换取零信息。

### 面板写操作只开四扇门

面板能写的东西只有四件，而且四件都不是新权力：

1. **建书。** `POST /api/inkwell/init` 直接调 `ProjectStore.init`，也就是 `novel_project action="init"` 调的那个函数，所以两条路落在磁盘上的字节相同。门禁本来就无条件放行 `init`（没有项目就没有可保护的东西），面板因此没有扩大任何权限。v0.11 起建完还会调宿主的工作区服务（`create({ path })` → `connectWorkspace` → `openSession`），这不是插件的写操作，是**用户点了一下之后宿主替自己做的那件事**。
2. **把会话钉到一本书。** `POST /api/inkwell/pin` 写的是 `<DSH_HOME>/inkwell/sessions.json`，与 `novel_project action="open"` 同一个文件、同一个键。它不动书里的任何东西，只回答「这个会话看哪本」——而这个答案本来就存在（v0.10 的换书工具就是它），面板只是让建完书的那一刻不必手动再说一次。
3. **给智能体挑模型。** `POST /api/inkwell/roles` 写的是 `project.json` 的 `roles`，与 `novel_roles action="set"` 同一个字段、同一个三态语义（省略＝不管、有值＝钉住、空串＝清掉这一层）。模型清单来自宿主的 `llm` 服务而不是插件自带表，因此「面板里能选的」恰好等于「dsh 里配过的」。
4. **改一条已经存在的东西。** `POST /api/inkwell/entry` 只改**已有**的角色卡、设定条目、章节正文：角色与设定走 `upsertCharacter`／`upsertWorld`（`novel_canon` 的那两个函数），正文走 `saveChapterBody`（`novel_chapter action="write"` 的那一个）。它不能新建角色、不能改章纲、不能推阶段、不能记账本事实——那些需要「理由」，而面板没有地方放理由。

四条约束写在这四个动作上，缺一条都会变成一次「安静的破坏」：

1. **必须带 `x-dsh-plugin: inkwell` 头**——跨站的简单表单提交设不了自定义头，这是同源之外唯一能拦住的东西。
2. **目录必须是绝对路径**——相对路径一律 400，绝不让宿主进程的 cwd 替用户猜一个位置。
3. **插件的 `root` 是绝对路径时拒绝建书**（409）——那时全书只有一个固定位置，面板上的「选目录」是谎话，不如直接说清并让用户改用工具。
4. **正文写入前先问一遍闸门**：`writeEntry` 对章节先跑 `gateToolCall('novel_chapter', {action:'write', number})`，非空就把那句话原样作为 409 返回。这样「章纲没批准就写不进去」这条规则只写在 `gate.ts` 里一次，面板只是它的第二个调用者。

选目录优先走宿主自己的选择框（`ctx.uiWorkspace.pickDirectory()`，由 `dsh-client-ui-workspace` 提供），读的是**惰性** `ctx.get('uiWorkspace')` 而不是声明进 `inject`：老宿主没有这个服务时，整个客户端包不该因此不激活，面板退回自己的目录浏览器。v0.11 又细分了一层：`hostCanPick()` 把「宿主没有选择器」和「用户点了取消」分开，只有前者才该把用户推进另一个页面——**取消是一次回答，不是一次失败**。

换工作区那段同理靠惰性服务：`ctx.get('workspaces')`（`dsh-api-workspace-controller`）+ `ctx.get('uiWorkspace')`。宿主缺一个就返回一句「书已经建好，在书库里点它就能进来」，而不是抛错——建书是插件能独立完成的事，换工作区是宿主的能力，两件事不该绑在一起成败。

`openSession` 的签名是 `openSession(target: SessionTarget)`，`SessionTarget = SessionId | SubagentAddress`，**直接传 id**。传 `{ sessionId }` 不会报错，只会静默不动——这类「参数形状对了但语义错了」的调用，靠类型看不出来（客户端包不带类型检查），只能读宿主自己的调用点。

`roles` 的路由来源一度全标错：配置 schema 会把四个角色物化成 `{}`，而旧判据只看「这一层存不存在」，于是四个角色都显示 `全局默认`，实际跑的是会话模型。判据改成「这一层有没有真字段」——**空对象不是一层**，这条同样适用于将来的任何覆写表。

已写章节的标题一度被章纲盖住：面板上改完标题、页面仍显示旧名。判据改成「有正文就看正文的标题，没正文才看章纲」——**章纲是提前给的名字，改过的名字是这一章现在的名字**。这类「两个来源谁说话」的错，测试里必须有一条，否则下次还会踩。

### 右侧栏只有一条

Web shell 的右列（`rightbar`）已经被右侧 Sidebar 占满，没有第二个右手座位。想往里加 UI，唯一被支持的办法是给那个 Sidebar 加**一个 tab 类型**（`ctx.sidebarRightTabs.register`）。抢占整栏会把 Sidebar 挤走，那不是扩展，那是覆盖。

## 入口形状是个陷阱

装载器把模块规整成 `exports.default ?? exports` 再交给 Cordis。所以一个 `export default apply` 会把 `inject` 一起挡在外面：插件于是在 `ctx.tools` 就绪前访问它，真机启动报

```text
cannot get property "tools" without inject
```

而单测完全看不见——它们直接调 `apply(ctx, config)`，跳过了装载器。现在有两道闸：`test/plugin-shape.test.ts` 断言模块形状，`scripts/verify-install.mjs` 对构建产物再断一次。教训写在这里：**入口导出的形状是契约的一部分**，不是风格问题。

## 三件写在书里的东西（v0.10）

**审稿意见是文件，不是聊天记录。** 每一轮 `novel_dispatch` 都把意见追加进 `<项目>/reviews/<三位章号>.json`：

```json
{ "version": 1,
  "rounds": [ { "round": 1, "role": "logic", "model": "deepseek/deepseek-flash",
                "at": "2026-10-25T09:12:00.000Z",
                "items": [ { "id": "001-r1-1", "severity": "error",
                             "code": "logic/time", "message": "…", "evidence": "…",
                             "state": "open", "note": "", "at": "…" } ] } ] }
```

`id` 是「章号三位-轮次-序号」，因为它会被人在对话里打出来（`novel_chapter action="review" number=1 id="001-r1-1" state="fixed"`）。`state` 三态：`open` 未结、`fixed` 已改、`waived` 决定不改——`waived` 必须带 `note`，否则半年后没人记得为什么留着它。**为什么不开成一条全局日志**：审稿意见的生命周期跟着章走，删章就该跟着消失，而不是留下孤儿。

**章节有版本号。** 每次落盘 `revision + 1`，写的时候要报出你读到的那一版（`writeChapter(draft, { baseRevision })`）。对不上就抛 `ChapterConflictError`，带着磁盘上的当前版本号回去让调用方重读。这是标准的乐观锁，**但它保护的是整章而不是字段**：两个人改同一章的不同段落，第二个人仍会被拒。字段级合并要一个 CRDT 或者行级 diff，对一个每章 2000–4000 字的仓库来说是过度设计——稿子是一个人的作品，不是共享文档。

**「哪本书」有三个答案，优先级也是三个。** 会话钉选（`<DSH_HOME>/inkwell/sessions.json`）> 会话 cwd 解析（`perWorkspace`）> 进程期 baseStore。钉选最具体：你说了「这个会话在看雾港」，那就别拿工作目录再猜一遍。这两个文件都在**状态目录**而不是项目目录里，因为它们描述的是一台机器上「你正在看什么」，不是这本书自己的事实——换台机器该重新选，而不是继承别人的窗口状态。这三个文件（`books.json`、`sessions.json`、两种 JSON）全部同步读写：`storeFor` 在每个工具体与门禁里被同步调用，它不能在知道是哪本书之前 await。

## 导入是一份计划，不是一次迁移（v0.12）

已经写到八十多章的人最想干的事是「把我的稿子拿进来」。这件事有两个陷阱：拿错东西覆盖掉原稿，和按名字替人编设定。

**扫描与写入是两个函数，中间隔着一份计划。** `src/domain/import-scan.ts` 全是纯函数（收字符串、出对象），不碰磁盘，因此能脱离 Harness 单测；`src/domain/manuscript.ts` 负责读盘并把计划压成一段人话；`src/domain/import-apply.ts` 才写。于是 `scan` 可以对着一个还不存在的书跑——「建之前先看一眼这个文件夹里有什么」正是面板建书弹窗要的语义。

**章号从文件名来，因为那是唯一可靠的锚。** `正文/第N章-标题-v1.md` 里认全角数字、认 `-v1` 这种版本后缀；同一章有两份文件时取更长的那份（作者通常是把短的那份留作废稿）。文件里重复的 `# 第N章 标题` 会被剥掉，否则会和面包屑里的章名打两次架。**为什么不用文件大小或修改时间排序**：章号是作者写下来的意图，时间戳是编辑器的行为。

**人物稿按小节关键字分派，认不出的不扔。** `## 外在底色` → 外形，`## 隐性欲望` → 目标，`## 心理阈值` → 秘密，含「说话／语气／口吻」的 → `voice`，其余（关系网、成长线）原样进 `card.notes`。宁可多一个 `notes` 字段，也不把关系网塞进 `secret` 硬凑——**塞错字段比没有字段更糟**，因为后面的 `novel_canon` 会把它当成一条设定来引用。

**绝不替用户编 `voice`。** 人物稿里没写说话方式，卡上就留空，扫描报告点名缺哪几张。阶段闸门（`src/domain/phase.ts`）要求每张卡都有 voice 才能推进，于是这件事在面板上是个待办，而不是一句「请自行补充」的提示。**这是这个插件存在的理由**：按名字猜一口腔调，正是「所有角色一个调子」的起点。

**导入是幂等的。** 已经存在的章默认跳过（`overwrite=true` 才重写），再导一次只补新章。作者的工作流是「在外面写几章，回来导一遍」，不是「搬一次家」。



`files` 只发 `lib/` 和手写的 `client.js`，所以**服务端半边必须发生在安装时**：从 git 安装的包没有预构建产物，靠 `prepare` 脚本在 install 后跑 `tsc`。pnpm 默认拦构建脚本，这也是为什么 README 要求 `allowBuilds: { dsh-inkwell: true }`——少了这一条，装上去是一个没有 `lib/` 的空壳，而 `dsh` 只会在装载时报一个看不出原因的错。`client.js` 没有构建步骤，也**不能有**：它是一层 `__ModuleLoader__` 信封，任何打包器都会把这层信封改写成别的东西。

`npm run verify`（`scripts/verify-install.mjs`）专治这类回归：它用假上下文挂载**构建产物**，断言 13 个工具、1 个门禁、1 条面板路由都出现了，还检查浏览器半边——`dsh.client` 声明、`exports["./client"]`、`client.js` 真在 `files` 里、文件里确实调了 `__ModuleLoader__.load`。测试跑的是 `src/`，这些打包错误它一个也看不见。

## 地点是历史，故事点是边界，时间是算出来的（v0.14）

长篇里三类错误各有各的形状，所以它们各自有一份记录，而不是挤进同一个容器。

**地点（`PlaceCard.state: PlaceState[]`）存的是「从第几章起它变成什么样」。** 一个地点不是一条设定：第 1 章是废弃货舱、第 30 章烧了一半、第 40 章改成仓库。写第 45 章时要看到的是第 40 章那一版，所以 `detail` 只是「现在的样子」，真正的数据是 `state` 那串按章的历史。这条设计带来一个必须守住的约束：**任何整卡替换的写入路径都必须搬运 `state`**——面板的 `kind=place` 写路由在 `src/panel/serve.ts` 里显式接住，和 v0.12.1 里 `notes` 被吃掉是同一个坑。

**故事点（`src/tools/story.ts`）是负向约束。** `add` 在上一段没收尾时拒绝，因为两段故事共用一个故事点不会报错：新章会自动继承旧故事点的 cast 与 places，等到读者发现「这个人怎么突然认识他」已经是二十章之后。拒绝时才有人去看。`close` 记录结束章，`at` 回答「第 9 章属于哪一段」——这是 `novel_briefing` 与审核员判断语气连贯的依据。

**时钟（`src/domain/clock.ts`）只存正文说过的话，日期是算出来的。** 这是那个模块存在的理由：两份日期就是一个人把二月的事记成十二月的开始。所以项目里只存 anchor（「第 1 章是 2019-03」）与 span（「第 1 到 4 章过了两三个月」），任何被读到的日期都由 `resolveTimeline` + `windowAt` 现算。

- **时间是区间，不是点。** `parseDuration` 把「两三个月」解析成 60–90 天，「一年多」解析成 365–730 天。假装精确的检查只有两种结果：误报诚实的正文，或漏掉真错。
- **算不出来就说算不出来。** 没有锚点、或锚点与跨度之间缺一段，`windowAt` 返回 `undefined` 而不是猜一个日期；`novel_timeline action="at"` 会回「还不知道」。空字符串比错答案好。
- **解析失败是错误，不是降级。** `parseWhen` 只认 `2019` / `2019-03` / `2019-03-15`，别的写法抛 `ClockFormatError` 并在消息里给例子。静默忽略会让人以为记上了。
- **回忆要对着时钟验。** `recall` 把「某人第 N 章说第 M 章那事发生在 X 月」落盘，`novel_check action="timeline"` 用 `checkProseAgainstClock` 比对时间窗——这是「长书里人物记错时间」唯一能自动发现的地方。

**面板不写时间线。** `src/panel/serve.ts` 对 `kind=timeline` 直接拒绝，理由写在错误消息里：日期是对正文的断言，而面板里没有那句正文。工具会连原句一起存下来，面板没有这个上下文——**能写不等于该写**。

## 导出是抄出去，删除是扔掉；两件都不该有机会碰到原稿（v0.16）

书能搬进来，就得能搬出去、能丢掉。这两件事看起来是「文件操作」，其实是两个关于边界的判断。

**导出只读、只写目标目录。** `src/domain/export.ts` 是纯函数（`bookText` / `volumeFiles` / `canonMarkdown` / `safeFileName`），面板的 `exportBook` 与工具的 `novel_export` 都只是把它拼出来的文本写到某个目录。所以导出不会改书里的一个字——导出失败最多是没有文件，不会有一本书半残。`dir` 必须绝对：相对路径意味着「宿主进程当时在哪」，那是 v0.2 串书事故的同一类假设。

**删除只碰 `.novel`，而且是先摘书架再删磁盘。** `removeBook` 的第一道判断是 `basename(root) === '.novel'`，不满足就是 400，不是「尽力而为」。理由是失败模式不对称：写错一个路径，导出只是少一个文件，删除是不可逆的。用户的稿子住在 `…/待定v2/.novel` 旁边的 `…/待定v2/正文/`，两者只差一层目录——所以路径形状本身必须是被检查的，而不是靠调用方小心。顺序也很重要：`forgetBook`（改 `books.json`）先于 `rm`，这样中途失败留下的是「书还在但不在书架上」，而不是「书架指着一个不存在的目录」。

**删除前问一句，是产品决定，不是流程装饰。** 一个不可逆的动作如果和「打开这本书」长得一样（同一张卡上的链接），就必须有一个停顿。`DeleteDialog` 的第一句是「删除后不能恢复。」，主按钮是「先导出，再删除」，直接删的入口要勾选之后才能按——把「留一份」放在最显眼的那个按钮上，是因为绝大多数人会想留一份，只是平时没想到。

**常红的删除链接。** `.iw-link.iw-danger` 在常态就是红的，不是 hover 才红：一个悬停才变红的删除按钮，在误点之前看着和「导出」一模一样。这条踩过一次坑——`S.linkButton` 里的 inline `color` 压过了 class 规则，红根本没生效；**inline style 永远赢过选择器**，颜色得交给 CSS。

## 卷是数据，窗口是视图（v0.17）

正文抽屉里有两件事一直混在一起：一本书的章节**属于哪一卷**，以及**列表画多少行**。前者是内容，后者是渲染，混在一起的后果是改一个要动另一个。

**卷号只有一个来源：`ChapterPlan.volume`。** 自动划分、手动归卷、拿回未分卷，三个入口写的是同一个字段，`0` 表示未分卷（沿用 `src/panel/tree.ts` 早就有的判断）。没有新增 `Volume.members` 之类的反向列表——反向索引一旦成为第二份事实，就一定会和第一份打架，而这正是「事实账本」那一节反复引用的失败模式。需要「每章在第几卷」时用 `membershipOf(plans, numbers)` 现算，代价是一次 O(n) 遍历，收益是没有同步代码。

**没有章纲的章节要有一张壳卡。** 卷号住在章纲里，那么「正文有、章纲没有」的章节（导入时大纲没覆盖到的尾巴）就无处记录卷号。`splitVolumes` 因此先 `shellPlan(number, volume, written)` 造一张只有卷号与标题、`beats: []`、`approved: false` 的壳章纲。它不是伪造大纲：`beats` 为空意味着章纲合同对它没有约束，它唯一承载的事实是「这一章在第几卷」。

**重新划分是搬章节，不是删章节。** `assignVolume` / `splitVolumes` 只写 `plan.volume`，从不 `rm` 章节草稿，也不删旧卷——`split perVolume: 5` 把 1–5 章并进第 1 卷时，第 2、3 卷仍然在，只是空了。这既是安全（用户的 3000 字不会因为一次点错消失），也是可解释（卷是书的骨架，骨架该由人拆）。

**长列表的窗口是渲染细节，不是数据模型。** `client.js` 的 `VirtualRows` 在「子节点全是叶子且超过 40 个」时接管：只挂载 `WINDOW_H / ROW_H + 2 * OVERSCAN` 行，用 `translateY` 定位。判定条件是「扁平叶子」，因为嵌套的树行高度不一致，窗口化会在折叠展开时算错位置——**先确认形状，再谈优化**。40 这个门槛写成了常量 `VIRTUAL_AT`，因为「什么时候开始窗口化」是可调的产品判断，不是物理常数。

## 章卡是记录，章纲是合同（v0.18）

一张章卡以前就是章纲：计划、节拍、钩子，写在同一个对象上。写到第八十几章才发现，回头查「那一章到底讲了什么」时，章纲回答不了——它记的是**打算**写什么。

**同一张卡上住着两种事实。** `ChapterPlan.summary/events/scene` 是事后记录：故事梗概、关键事件、场景。`beats/hooks/characters` 是事前承诺，写正文时必须兑现，改了要重新批准。两者必须能分开改，所以 `card` 动作与 `add_chapter` 分开，且 `card` 的返回值明说「不改变章纲合同，也不需要重新批准」。

**合并写，不整卡替换。** `updateCard` 只改传进来的字段，`undefined` 是「不动」，空串是「清掉」。这条原则在 v0.12.1 付过学费：那次整卡替换把导入的 `notes` 抹掉了，而抹掉是静默的——页面看起来还成功了。任何「保存整张卡」的路径都必须显式接住没提到过的字段。

**名字要对得上是硬约束，正文里出现了谁不是。** `card` 里写的角色必须存在于角色卡（否则搜索与上下文包会漏掉这个人）；而「正文里真的叫出了谁的名字」是**派生显示**（`presentInText`），只给人看，绝不喂给章纲合同——把派生结果塞回合同，校验就变成了自说自话。

**导入的书本来就有正文，所以它的空壳章纲可以被视为已批准。** 大纲没排到的尾巴章节（用户那本是第 84、85 章）没有章纲，闸门连面板保存都不许。补壳时区分两种：已有正文的补成 `approved: true`（没有节拍可违反，不批准只会把页面锁死），没有正文的仍是未批准、闸门照旧。这一步必须在 `gateToolCall` 之前——闸门问的就是章纲。

## 角色卡是档案，关系只存一侧（v0.19）

角色卡以前只存「怎么写他」：说话方式、外貌、目标、秘密。`aliases`/`personality`/`stages`/`relations`/`status` 补的是「他是谁」——写到第八十几章，要查的是后面这几项。

**关系写在声称它的那张卡上。** `CharacterCard.relations: { name, kind }[]` 只存在于一侧；另一侧由 `inboundRelations(cards, name)` 在渲染时反查，显示成「别人写的」。同一条事实存两份必然对不齐（改了一边忘了另一边），而反查是零成本的——整本角色卡本来就在内存里。

**名字对不上是允许的，但要说出来。** 关系里写的人如果还没有角色卡，`entry.ts` 仍然显示这一行，只是加一句「角色卡里还没有这个人」。先有人物再有卡是正常写作顺序；`novel_outline action="card"` 的 `characters` 则相反——章纲要按名字搜上下文，名字必须已经存在，所以那边是硬拒绝。这两处的严格程度不同是故意的。

**别称也是名字。** `answersTo(card, name)` 同时看 `name` 与 `aliases`。导入时 `splitHeading` 把括注里的名字放进 `aliases`（`# 刘紫灵（网名刘格格…）` → `['刘格格','格格','刘紫灵']`），卡名保持原样——改名会让已经在盘上的旧卡和新卡并排存在。

**写入口只有一个。** 面板与 `novel_canon` 都调 `updateCharacter(store, name, patch)`：`undefined` 保留、空串清空、空列表清空，且「保留」是在合并层显式写的，不是靠调用方记得。v0.12.1 的整卡替换事故（导入的 `notes` 被静默抹掉）就是没有这一层。

**导入只填空着的字段。** `import-apply` 对已有的卡走 `updateCharacter` 且只提交空字段；`relations`/`stages` 合并时按「左侧名字」去重，重导同一个文件夹不会把关系翻倍。这条与「一句话前提只在空着时填」是同一条规矩：导入永远不许盖掉人写的东西。

## 审稿窗口有预算，章卡有版本（v0.20）

审稿人以前只拿到待审这一章：正文、章纲合同、相关账本事实、角色卡。前面八十几章它一章没读过，所以「跨章一致性」不是模型能力问题，是材料问题。

**窗口从最近往回装，装不下的是最老的那章。** `buildReviewWindow(snapshot, drafts, target, options)` 取 `number < target` 的章，最近 `full` 章给全文、再往前 `recap` 章给梗概，总量受 `budget` 约束。超预算时把**最老**的那章降级成梗概而不是丢掉，也不动离得最近的那一章——连续性断在衔接处，紧挨着待审场景的那一章一个字都不能少。降级而不是截断：截断会给一个「说到一半」的假象。

**梗概有两种来源，必须标出来。** 优先章卡 `plan.summary`（人写的）；没有卡就退回 `ChapterMeta.summary`（正文末段截出来的），标 `source: 'tail'` 并在提示词里写「取自正文末尾，不是人写的梗概」。让审稿人知道自己看的是摘要还是摘录。

**说不出来的要说不出来。** 窗口外的章节数写进提示词（「更早的 N 章不在这次审稿范围内，不知道就说不确定」）。宁可它承认盲区，也不要它拿想象补连续性。

**章卡记版本，正文改了就"过期"。** `ChapterPlan.cardRevision` 记章卡写自哪一版正文；`updateCard` 只在 `summary`/`events`/`scene` 被给到时盖章（改节拍、标题不算——那是「应该发生什么」）。`cardIsStale(plan, meta)` 只比两个整数，于是三处显示是同一条判据：`novel_check action="cards"`、章节页一栏、抽屉行标。**修法只有一条**：按当前正文重存一次章卡。

**过期不是错误。** 它不进 `errors`，也不阻断写入——正文本来就该能改，章卡本来就该跟着改。系统能做的是别让它在无人知晓的地方一直旧下去。

## 关系是一张表，不是一句话（v0.21）

- **一句话只装得下一半。** 「刘紫灵：母女，但彼此不认」写的是刘紫灵怎么当王上的妈，没有写王上怎么当她儿子。两侧各存一份，改一边另一边就旧；只存一侧，另一侧永远是别人的转述。所以关系从卡上搬进 `canon/relations.json`，一条边两个端都写名字。
- **`kind` 有方向，`reverse` 是反过来那一面。** 一条边只允许一个方向，另一面的说法存 `reverse`，这样两页读的是同一条记录，而 `seenFrom` 能各说各的。`symmetric`（夫妻、兄弟）是显式声明的：同一个词两边都通，此时 `reverse` 写了别的词就是矛盾（`relations/contradiction`，error 级）。
- **谁在哪一页改，都不能把方向翻过来。** 在 `from` 那页改的是 `kind`，在另一页改的是 `reverse`。反过来做（按当前页重建一条 `from` 指向对方的边）等于把另一端的原话删掉——这正是 v0.21 之前「别人写的」那块让人不放心的地方。
- **认人要认括号里的写法。** `晨琳（端木晨琳）`、`端木晨琳（晨琳）`、`刘紫灵（网名刘格格，正文里直接叫「格格」）` 都是同一个人。`nameTokens` 按括号与分隔符切，`sameName` 要求有**一整段**相等——所以 `王上势` 不会被认成 `王上`，`大格格` 不会被认成 `格格`。真书上这一条把 7 条「对不上角色卡」的假报降成了 3 条真的。
- **卡上不留副本。** 迁移后 `CharacterCard.relations` 不再写盘；`updateCharacter` 是唯一入口，它读写边表并把卡上的旧字段删掉。任何整卡替换的地方（导入、`upsert_character`）都必须记得这一点，否则会复活一张会过期的副本。
- **对不上的人不算错。** 写到一半的书本来就有人还没开卡；`relations/unknown-person` 是 info，页面标一句「角色卡里还没有这个人」，不拒绝写入。

## 时间线是投影，不是第二份数据（v0.22）

- **线由时钟算出来，不存。** `src/domain/spine.ts` 的 `buildSpine` 只读 `snapshot`：起点、年点、事件位置全部从 `bookStart` 与 `resolveTimeline`/`windowAt` 现算。所以改了锚点，线立刻跟着变，不存在「时间轴数据过期」这件事。
- **起点是一个决定，不是一次推断。** `bookStart` 钉在 `project.json` 里；钉住之后所有年点从它数。没钉就退回第一个锚点，两者都没有就说「还没有任何日期」——**不拿今天的日期凑一个起点**，那会让整条线都是假的却看不出来。
- **年点用「同一个月日」推进。** `addMonths(start, 12k)`，2020-10-14 的下一个点是 2021-10-14，不是 2021-01-01。跳到 1 月 1 日等于替作者决定这本书按日历年分年，而年只是标注，不是设定。
- **一年一个点，但点到最后一个事件为止再补一个点。** 停在最后一个事件上等于声称故事到此结束，`buildSpine` 没有这个权限。
- **一章一个气泡。** 同一章既有锚点又有章卡正文时，锚点那句话并进 `note`（渲染成「锚：…」），不另画一个。八十五个气泡里混进八条重复说明，读的人会以为那八章多写了一个事件。
- **没有日期的章不上线，也不藏起来。** `loose` 收它们，面板列前 10 条 + 「还有 N 章没有日期」。假装它们在第 1 章那天，是这份模型里最容易说不清的谎。
- **面板只写起点。** 时间线页的 `edit.inputs` 只有 `start`；`writeEntry` 遇到 `kind === 'timeline'` 只接受 `fields.start`，其余一律 409 并指回 `novel_timeline`。日期锚点仍只有一个入口。

## 打日期要能一次选一批（v0.25）

时钟有三条路，但入口只有一个：`addAnchor` / `addAnchors`。这不是洁癖，是本仓库付过两次学费的地方——`notes` 在 v0.12.1 被整卡替换吃掉，地点的 `state` 在 v0.14 被吃掉；同一个事实有第二个写入口，第二次写就会忘记搬第一个入口的字段。

三条规矩：

- **日期先校验，再写。** `parseWhen` 一次，失败则整批不落盘。半个时间线比没有时间线更难查：读者不知道缺的是哪几章。
- **同章覆盖，不新增。** 一个人说「第 7 章其实是 10 月」，是在改一条已知事实，不是加一条新事实；锚点的 id 保持不变，改的是 `when`。
- **选章列表取并集。** 已落盘的章与章纲里的章都算；只等正文写完才让填日期，时钟就来得太晚——大纲阶段正是该定的时候。

面板上是一个章号网格而不是四个输入框：输入框的形状来自「一次一章」这个假设，而假设本身是要改掉的东西。

## 日期从正文里读，但只读明说的（v0.23）

- **时钟只有一个写入口。** `src/domain/timeline-edit.ts` 的 `addAnchor` 是唯一往 `timeline/clock.json` 加锚点的地方：工具、面板、保存正文后的自动识别、导入后的整本解析，四条路都调它。理由是本仓库付过两次学费（`notes` 在 v0.12.1 被整卡替换吃掉，地点的 `state` 在 v0.14 被吃掉），凡是「两条路写同一份数据」，早晚会写出两种形状。
- **只认正文明说的日期。** `scanProseTimes` 认 `2020年10月14日`、`二〇二〇年十月十四日`、`三天后`、`又过了两三个月`、`第二天`；**不认**「那年秋天」「多日后」「开春」。季节不是窗口，模糊说法不是长度：猜一个日期等于往文件里写一条以后某章会撞车的错事实，而那一条会比没有更难查。
- **一章一个日期。** 同一章再说「傍晚」「半夜」是这一章的细节，不是第二个锚点。两个日期写在同一章上，`resolveTimeline` 自己就会开始打架。
- **矛盾只报不写。** 正文写「2025 年 6 月」，但这一章按已知的锚点与跨度算出来是 2020 年 3 月（差超过 `SLACK_DAYS = 90` 天），`adoptClock` 把它放进 `conflicts` 而不是覆盖时钟。抹平它就是抹掉唯一能让人发现问题的证据。
- **第一个明确日期就是起点。** 书还没有 `bookStart` 时，第一次读到绝对日期就把它钉成起点——这是「以第一个出现时间为起点」的落地，也是唯一允许自动写 `project.json` 的地方（且只写这一项）。
- **人的话优先于扫描。** 已经有锚点的章，`adoptClock` 不动它，只报一句「这次没动它」。
- **面板现在也能写锚点，但标成 `manual`。** v0.22 说「一种数据一个入口」，v0.23 加了 `source: 'manual' | 'prose'` 之后这句话仍然成立：入口还是一个函数，只是多了个说明「这条是谁说的」。将来要区分「人改过、别被扫描覆盖」时，这个字段就是依据。
- **时间一致性不用读前文。** `novel_check action="timeline"` 拿时钟比对每章的时间窗、回忆里说的日期、正文里写死的日期。省 token 是顺带的；真正的好处是它查的是全书，而审稿窗口只能看最近十来章。

## 上下文包要装人，也要装人和人之间（v0.24）

- **写手缺的从来不是「有谁」，是「谁和谁」。** v0.23 之前 `briefing.ts` 只按出场人物列角色卡；关系表存在了十几个版本，却从没进过包。于是模型知道这一章有沈砚和阿蘅，不知道阿蘅是他的债主，写出来的对话就是两个初次见面的人在互相试探。
- **关系按人分组，本章在场的排前面。** 一个人的边可能十几条，装不下全部；「本章在场」是最强的相关性信号，因为它决定这一章表面上的礼貌与暗地里的立场。剩下的按文件顺序取三条，够了。
- **地点给的是「截至这一章」的状态，不是 `detail`。** 地点是历史（v0.14 的设计），`states` 里最后一条 ≤ 本章的就是现在。给最初的描述，等于让写手把一个已经烧掉的码头写成还在。
- **地点相关性靠章纲点名，不靠全量。** 一本书几十个地点，全塞进去就是噪声；章纲的标题/场景/梗概/节拍/钩子里出现过的名字（含别名）才算这一章要用。没点名时给最近十章出现过的三个，并标注「最近出现于第N章」。
- **空的时候要说空。** 「关系表里没有这几个人」「章纲没有点名地点」比不出现更有用：它告诉作者该去补哪一侧，而不是让写手悄悄发明一套关系。
- **同一个人不能有两条边。** `relationId` 拿写下来的名字做主键，别名一多就会给同一对人两条边——用户那本《待定》19 条边里有 5 条如此。读表时按卡名归一（`settleRelations`），第二条的说法折进备注，边数从 19 降到 14。

## 后续方向

- **docx / epub 导出**：`src/domain/export.ts` 已经是纯函数，只把文本拼成文件；接一个 OOXML 或 EPUB 打包器是纯增量，v0.16 的 `/export` 路由不用改形状（多一个 `format` 取值即可）。
- **面板里能不能批准章纲**：v0.5 让面板建书（与 `init` 同一个函数），v0.6 开了「挑模型」（与 `novel_roles` 同一个字段），v0.8 开了「改已有条目」，v0.10 开了「改正文并结案审稿」。再往前一步到「批准章纲」只剩一个障碍：批准需要理由，而理由要写进 `plans`。可行做法是让面板的批准表单要求填一句理由，再走与 `novel_outline` 相同的 `approved` 写入——**门禁的唯一性不是「只有工具能写」，而是「只有一条代码路径能写」**。
- **有争议时串行审稿**：现在三位审核员各跑各的，意见并排落盘但没人读对方的。依赖图能让 chief 真正裁决分歧，并把「分歧」本身记成一条 review item。
- **批量补齐 `voice`**：v0.12 导入后会有 N 张卡缺说话方式（真机上 6 张全缺）。它们是一件待办，缺一个「一次填完 N 张」的页面——现在只能一张张点进去。
- **卷自己的那几行**：v0.17 改的是「哪些章属于哪一卷」，卷的标题与梗概仍然只能由 `novel_outline action="add_volume"` 写，面板里不能改名、不能把一卷拆成两卷（只能整体重划）。
